File Management
Best Practices for the Workplace

Naming, structuring, storing, and retiring the files your colleagues will need to find long after you've forgotten you made them.

Kay P. · Scholarly Engagement Librarian & Resource and Data Analyst
Howard-Tilton Memorial Library, Tulane University
kmaye@tulane.edu
The problem

The file exists. Nobody can find it.

Poor file management rarely destroys anything outright. It just makes work slower, duplicative, and dependent on whoever remembers where things are.

Lost time

Searching for, recreating, or re-requesting documents that already exist somewhere on a shared drive.

Duplicate truth

Three versions of the same budget, all slightly different, none clearly current.

Single points of failure

Files that live on one person's desktop leave with that person.

Compliance risk

Records kept too long, deleted too soon, or shared with the wrong permissions.

The working standard

A colleague who has never seen your project should be able to find the current version of a file, know it's current, and understand what it is — using only the folder path and the filename.

Roadmap

Six decisions, made once

Good file management isn't discipline applied daily — it's a handful of conventions agreed on once, then followed without thinking.

1 · Where files live

Choosing storage on purpose instead of by default.

2 · How folders nest

Shallow, predictable structures anyone can navigate.

3 · How files are named

Conventions that sort, scan, and survive.

4 · How versions are tracked

One current file, an unambiguous history.

5 · How access is granted

Permissions, sensitive data, and sharing.

6 · How files retire

Retention, cleanup, and handoff.

Decision 1

Storage is a decision, not a habit

The desktop and the email inbox are where files go when nobody decided where they should go. Match the location to how the file will be used.

LocationUse it forWatch out for
Team / department site
(SharePoint, shared drive)		Anything more than one person needs, now or later. Team records, procedures, reports, project files.Requires an agreed structure — otherwise it becomes a landfill.
Personal cloud drive
(OneDrive, Google Drive)		Drafts in progress, personal working notes, files only you use.Departs with the employee. Not a home for team records.
Local desktop / laptopScratch work and temporary downloads.Usually unbacked and invisible to everyone else.
Email attachmentsTransmitting a copy. Never storing the original.Forks the file into as many versions as recipients.
System of record
(HR, finance, CRM, ticketing)		Data and content the system is designed to hold.Keep exports labeled as exports — they're snapshots, not sources.

Rule of thumb

If losing the file would create work for anyone besides you, it does not belong in a personal location.

Decision 2

Broad and shallow beats deep and clever

Deep hierarchies hide things. Aim for three or four levels, with top-level folders that match how the work is actually organized — by function or project, not by person or file type.

Avoid
Shared/ ├── Jordan/ │ └── stuff/ │ └── new folder/ │ └── misc/ │ └── budget final.xlsx ├── Documents/ ├── PDFs/ └── Old files (DO NOT DELETE)/

Organized by person and format. Unnavigable to anyone else.

Prefer
Operations/ ├── 01_Budget/ │ ├── FY2026/ │ └── FY2027/ ├── 02_Reports/ │ ├── Monthly-Metrics/ │ └── Annual-Summary/ ├── 03_Projects/ ├── 04_Meetings/ └── _Archive/ ← closed, kept

Organized by function. Numbered prefixes hold sort order.

Three habits that keep structure usable

  • Number top-level folders only where order carries meaning; otherwise let them sort alphabetically.
  • Give every folder tree one _Archive or _Closed folder so completed work has somewhere to go besides deletion.
  • Put a short README.txt in shared project folders: what this is, who owns it, what's current.
Group activity · 20 minutes

Map your team's files

In groups of three or four, from the same team where possible. Work on paper first — the structure matters more than the tool.

Step 1 · Inventory (5 min)

List every kind of file your team creates or receives in a normal month. Kinds, not individual files: budget worksheets, meeting minutes, vendor quotes, training materials, system exports.

Step 2 · Group (5 min)

Sort that list into six to nine categories. If a category holds one file, fold it into another. If it holds forty, split it. These become your top level.

Step 3 · Nest what needs nesting (5 min)

For each category, decide what the level below it divides by — fiscal year, calendar year, quarter, project, or nothing — and keep going only where the work really is that layered. One pattern per branch, applied consistently.

Step 4 · Assign and test (5 min)

Name an owner per top-level folder. Then test it: pick three real files and say aloud exactly where each one goes. Any hesitation is a flaw in the structure, not the person.

Two questions to settle before you leave the table

  • Where does work-in-progress live, and when does it move into the shared structure?
  • Which categories hold restricted material and therefore need their own permissions?

Decision 3

  
A filename is metadata

  

  
Filenames are the only description most files ever get. Six conventions cover nearly every case.

  

    
Lead with what sorts
Date first for anything recurring; project code first for anything grouped.

    
Use ISO dates
YYYY-MM-DD or YYYYMMDD. Sorts chronologically and reads the same in every country.

    
No spaces
Hyphens between words, underscores between elements. Spaces break URLs, scripts, and command lines.

    
Letters, numbers, - and _ only
Skip / \ : * ? " < > | # % and &. They break syncing and cross-platform access.

    
Pad your numbers
v01 not v1, 03 not 3 — so 10 doesn't sort before 2.

    
Keep it under ~60 characters
Full paths have limits. Describe, don't narrate.

  

  

    
A pattern that works for most workplace files

    
YYYY-MM-DD_Project_Content-Description_v01_INITIALS.ext

    
Drop any element you don't need — but keep the order consistent across the folder.

Decision 4

  
“FINAL_v2_revised” is not a version system

  

  
Versioning fails when the label describes a feeling instead of a state. Pick one scheme and use its vocabulary literally.

  

    

      
Sequential numbering

      
    
        
  • v01, v02, v03 — every meaningful save
    • 
        
  • v02-1 for minor edits between drafts
    • 
        
  • APPROVED or PUBLISHED replaces the number once signed off
    • 
        
  • Superseded versions move to _Archive, they don't sit alongside the current one
    • 
      

    

    

      
Let the platform do it

      
    
        
  • SharePoint, OneDrive, and Google Drive keep version history automatically — one file, full trail
    • 
        
  • Co-author in place instead of emailing copies around
    • 
        
  • Use a version control system for code and scripts, not filename versioning
    • 
        
  • If the platform versions it, don't also version the filename — pick one
    • 
      

    

  

  

    
Name a file owner

    
For any shared document, one person is responsible for merging edits and declaring which version is current. Versioning schemes fail for social reasons far more often than technical ones.

  







  
Durability

  
Choose formats that outlive the software you made them in

  

  
Working formats are for editing. Durable formats are for the copy that still has to open in ten years.

  

    
ContentWork inKeep a copy inWhy

    
      
Documents.docx.pdfFixes the layout so it opens the same way anywhere

      
Tabular data.xlsx.csvPlain text, no formula or version dependency

      
Images.psd / .ai.tif / .pngLossless and widely readable

      
Notes & documentation.docx.txt / .mdReadable by anything, forever

      
Presentations.pptx / .html.pdfSurvives missing fonts and links

    
  

  

    
Watch for data loss on export

    
Saving a spreadsheet as CSV drops formulas, formatting, and every tab but the active one. Keep both files, and name the CSV so it's clear it's an export.

  







  
Decision 5

  
Permissions are part of the file

  

  
Sharing settings drift. Files get moved, links get forwarded, staff change roles. Handle sensitivity at the point of saving, not at the point of an incident.

  

    
Share the location, not the file
Send a link to the file in its home location. Attachments create copies you can't update or revoke.

    
Grant the narrowest access that works
View rather than edit; named people or groups rather than anyone-with-the-link.

    
Separate sensitive material
Personnel, customer, contract, and confidential vendor files belong in restricted folders, not mixed into general project folders.

  

  

    
Before you save anything with personal data

    
    
      
  • Do you need the identifying columns at all? Strip or hash what you don't need.
    • 
      
  • Does the location's permission set match the data's sensitivity? Check the folder, not just the file.
    • 
      
  • Are vendor data or contract terms covered by an agreement that restricts redistribution?
    • 
      
  • Organizational policy — privacy, HR, legal, and records policy — governs before any convention on these slides does.
    • 
    

  







  
Insurance

  
Sync is not backup

  

  
A synced folder faithfully replicates deletions and corruptions. Backup means you can retrieve an earlier state after something goes wrong.

  

    
3 copies
The working file plus two others — not three names for the same synced folder.

    
2 media types
Company cloud storage plus a managed server or drive.

    
1 off-site
Geographically separate. In this region, that condition is not theoretical.

  

  

    
Test the restore

    
An untested backup is an assumption. Once a year, recover one real file from it and confirm it opens.

  







  
Decision 6

  
Files should retire on schedule

  

  
Keeping everything forever is a decision with costs: storage, search noise, and legal exposure. Retention converts that decision into policy.

  
    
    
  • Know which files are records. Anything documenting a decision, transaction, or obligation is probably governed by a retention schedule — check before deleting.
    • 
    
  • Distinguish records from working copies. Drafts, duplicates, and personal notes usually aren't records and can be cleaned up freely.
    • 
    
  • Set a disposition date when you create the folder, not when it's full. A line in the README is enough.
    • 
    
  • Archive before you delete. Move completed work to _Archive with a date; delete only what policy allows and nobody needs.
    • 
    
  • Suspend deletion under legal hold or audit. When notified, retention pauses entirely.
    • 
  

  

    
Ask before you purge

    
Retention rules differ by organization and by industry. Confirm with whoever owns records, legal, or compliance rather than deciding locally.

  







  
Upkeep

  
Small routines, not big cleanups

  

  
Annual file-purge projects fail because they're enormous. These four intervals keep the work small enough to actually happen.

  

    
Daily · 2 min
Empty the Downloads folder. File or delete anything saved to the desktop.

    
Weekly · 10 min
Name and file the week's working documents. Archive superseded versions.

    
At project close
Delete duplicates, mark the final version, write two lines in the README, move to _Archive.

    
Annually · 1 hr
Review the top two folder levels. Apply retention. Test one backup restore.

  

  

    
Handoff is the real test

    
Before someone leaves a role — or before you take leave — the team's files should already be in shared locations, named conventionally, with owners documented. If preparing for a handoff requires a week of file archaeology, the system needs fixing, not the person.

  







  
Making it stick

  
Conventions are a team agreement

  

  
Individual discipline decays. Written, shared conventions survive turnover — but only if they're short enough to read.

  

    

      
Write a one-page file plan

      
    
        
  • Where each category of file lives
    • 
        
  • The naming pattern, with three worked examples
    • 
        
  • Who owns which folders
    • 
        
  • What gets archived, when, and by whom
    • 
      

    

    

      
Lower the cost of compliance

      
    
        
  • Set up template folders new projects can be copied from
    • 
        
  • Add the naming pattern to onboarding materials
    • 
        
  • Rename opportunistically — when you open an old file, fix its name
    • 
        
  • Don't retrofit ten years of files; start clean going forward
    • 
      

    

  

  

    
Adopt over perfect

    
A mediocre convention everyone follows beats an elegant one only its author uses. Agree on something, write it down, revisit it in six months.

  







  
Take with you

  
The ten-item checklist

  

  

    

      
01
Shared work lives in shared locations. Not the desktop, not the inbox.

      
02
Folders are broad and shallow, organized by function, three to four levels deep.

      
03
Dates are ISO — YYYY-MM-DD, always.

      
04
No spaces or special characters in file or folder names.

      
05
Numbers are zero-padded so they sort correctly.

    

    

      
06
One current version, clearly labeled; superseded copies archived.

      
07
Links, not attachments, when sharing internally.

      
08
Sensitive files are separated and permissions checked at the folder level.

      
09
A clean copy exists in a durable format, backed up 3-2-1.

      
10
Every shared folder has an owner and a disposition date.

    

  

  
Adopt what your team will actually follow. Start with items 3, 4, and 6 — they deliver most of the benefit for the least effort.
